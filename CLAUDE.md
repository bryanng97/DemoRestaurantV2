# DemoRestaurant: Restaurant City–style game (Unity engine test)

Cozy 2D isometric restaurant sim for Android and iOS first, with Steam later. The first theme is Malaysia, and more countries arrive later as content packs.
The full brief is in the team handoff document. The rules below are binding.

## Naming

Use project or feature names for authored filenames, folders and Resources paths (for example, `ExteriorPrototype` and `ExteriorAssets`). Avoid reference-game titles in these names. Keep accurate source attribution in provenance documentation.

## Engine and versions (pinned)

- **Unity 6000.6.4f1** with URP 17.6 and the 2D feature set (`com.unity.feature.2d` 2.0.2). Input System 1.20 is the only input backend, so do not use `UnityEngine.Input`.
- Do not use APIs from other Unity versions. If an API is unclear, check the 6000.6 docs.
- C# 9 (Unity's compiler). No `System.Text.Json`, `Span`-heavy code or other APIs that IL2CPP does not support.

## Architecture rules

1. **Logic is separate from rendering.** `Assets/_Game/Scripts/Logic` is the `DemoRestaurant.Logic` assembly with `noEngineReferences: true`, so it cannot import UnityEngine. Customers, cooking, economy, inventory, pathfinding and depth ordering live there as plain C#. Unity code only reads that state and draws it.
2. **Every piece of game logic has unit tests** in `Assets/_Game/Tests/EditMode` (NUnit). If the game is ever ported, the tests are ported with it.
3. **Content is data-driven.** Dishes, furniture, customer types and prices come from JSON in `Assets/_Game/Resources/Content/<country>/`. Never hard-code content in C#.
4. **Each country is a content pack.** Adding one should mostly mean adding JSON and art, not code.
5. **All player-facing text goes through `Loc`** (`Resources/Localization/{en,ms,zh}.json`). Content uses `nameKey`, never display strings. Developer-only debug overlays such as `PerfHud` are exempt.
6. **The economy is server-authoritative.** Coins, rewards, gifts and timer completions are awarded or validated by the Supabase game API (`Docs/backend-api-requests.md` lists what is still missing). Client values such as `CustomerPaid` are predictions for display only.
   - Flow: `Wallet.Predict` shows the coins straight away, and `IEconomyServer.SubmitSale` sends the sale. `Wallet.Settle` then applies the server's amount.
   - `LocalEconomyServer` is the offline stand-in. It enforces the same rules the backend must: price taken from the server's own catalog, unknown dishes rejected, receipts settled once.
   - **Online (Supabase, API v2 on `player-api/v1`; contract in the backend repo's `docs/mobile-api-v2.md`):** `Scripts/Game/Online` holds `SupabaseAuth` (email sign-in, refresh), `GameApiClient` (retry rules, persisted `Idempotency-Key`s, `X-Ruleset-Version`, the `/config` ETag) and `OnlineSession` (start-up: bootstrap → `GET /config` → `POST /sync/ledger`, then a sync every 15 s and on pause). The sync rules are plain C# in `Logic/Online`: every player action is recorded by `RestaurantSession` in its `ServerLog` (`ServerActionLog`: one keyed ledger entry per action, applied locally at once, offline too); `OnlineSync` sends batches, folds each server state back (`RestaurantSession.ApplyServerState`: coins, XP and demand are the server's value plus what is still queued) and asks the game to adopt the server's restaurant when layout or staff differ (`SaveFromServer`, then a scene reload). On sign-in (`OnlineSync.OnSignIn`), an account that already has progress always wins: the device's queued actions are dropped and the account's restaurant loads. A brand-new account on a device with guest play asks the player whether to keep this device's restaurant (`ChoiceDialog`). A server restaurant that can't load locally is never forced: the local one is kept and the reason is logged. `ServerLayoutCodec` maps the local layout to the v2 layout document (the same grid convention; stable instance ids in `InstanceIdBook`); ids that differ are mapped in `Content/<pack>/server_ids.json`, and pieces the server's catalog doesn't sell stay local. JSON goes through `Logic/Online/Json.cs` (JsonUtility can't read maps). Check against the dev server with `npm run test:live:unity -- <dev ref>` in the backend repo (`Tools/OnlineSyncCheck`). The project key goes in the git-ignored `Resources/Online/OnlineConfig` (DemoRestaurant > Online > Create Online Config); without it the game runs offline and the log waits for the first sign-in.
7. **Kitchen flow** (`RestaurantSim.Kitchen.cs`, as in the reference game): a customer orders, which creates an `OrderTicket`. A chef cooks it at a free `Stove` (standing on the cell in front of it) for the dish's `cookSeconds` (its preparation time) divided by `cookSpeed`. The plate then waits on that stove, which stays busy until a waiter collects it and serves it; the customer then eats and pays. There is no serving counter. Each chef claims a stove as their `Station` and is placed straight onto its front cell (chefs never walk to stoves, so a stove walled in by tables still gets a chef); waiters must still reach the stove to collect plates.
   - **Drinks** (category drink, unlocked by the sheet's `drinksUnlockLevel`) are never cooked: a waiter walks to a free `DrinkMachine` (one waiter per machine), pours for the dish's `cookSeconds` and serves it. Guests only order drinks when a drink machine can be reached from the door.
   - **Toilets** (`RestaurantSim.Toilets.cs`, rules.json → `toilets`, as in the reference game): from `fromLevel`, a `chance` of guests use a free working `Toilet` after paying (`toiletSeconds`), then a free `Sink` (`sinkSeconds`) if there is one. No working toilet: the guest leaves unhappy. A toilet breaks after its `breakCount` uses (furniture.json) and stays broken until a cleaner fixes it (`fixSeconds`) or the player taps it. Uses are saved (`SaveData.toiletUses`).
   - **Waiters** appear at a post beside a stove reachable from the door (hired or at start) and walk back there between jobs (`RestaurantSim.Reach.cs`). Guests don't sit down when no stove can be reached from the door. Pieces nobody can reach don't block saving a renovation (as in the reference game); the player is warned instead. A room still needs a chair and a stove.
   - Customers order only from `RestaurantMenu.Active`, which is never empty. They pick a course first (starter, main, dessert, drink among those on the menu), then a dish in it.
   - A guest who sits on a chair with no table beside it complains and leaves unhappy after `noTableWaitSeconds` (rules.json; 0 in code defaults, so tests can use lone chairs). Slots are per dish category (starter, main, dessert, drink) and come from the restaurant level (`EconomyTable.MenuSlots`); drinks have no slots until they unlock.
   - Throughput is limited by chefs, stoves and waiters.
   - Furniture footprints follow the reference catalog: tables, chairs, stoves and most pieces are 1 x 1.
   - **Dining capacity:** one guest per table, even if several chairs touch it. The chair reserves its facing table (or the first adjacent table) as soon as the guest starts walking to it. Other chairs at that table remain unavailable through eating and dirty dishes. Offline throughput also counts distinct tables, not chairs. Packs whose `noTableWaitSeconds` is 0 still support lone chairs for tests.
   - **Dirty tables** (`RestaurantSim.Cleaning.cs`): a customer who paid leaves dishes, and the whole table can't be used until it's cleared (`cleanSeconds` divided by work speed, `cookSpeed` in `staff.json`). Cleaners clear tables; while no cleaner is on duty, idle waiters do it, so the restaurant never jams. Cleaners unlock at the level in the economy sheet's Staff tab. Players can tap an empty plate or its table to queue manual clearing (`playerCleanSeconds`, 5 seconds per task, sequential); tapping a waiting task cancels it, active tasks run to completion. Taking over releases the assigned employee. Manual clearing never awards a second sale. `TableCleaningFeedback` draws tap glow, progress and completion sparkles; world taps ignore UI, decoration mode, camera drags and pinches.
   - **Furniture is owned** (`FurnitureOwnership`): a new restaurant gets one stove and two tables with two chairs each. Everything else is bought in the build editor: placing more copies than you own is paid on Save (`ILandPurchaseServer.CommitLayout`, server prices), removed pieces go to storage, and `unlockLevel` (restaurant level) in furniture.json gates the shop. Ownership is saved in the layout save (`LayoutSnapshot.owned`); older saves own what they have placed.
   - **Room size** (`RoomGrowth`, rules.json → `roomGrowth`): as in the reference game the room grows with the restaurant level, for free, and never shrinks (`RestaurantSession.GrowRoom` on level-up and after loading; the server accepts any size up to what the level allows or the room already had). There is no indoor land to buy; the old per-step land price (`ExpansionRules`) is only used by packs without `roomGrowth`.
   - **Stacking** (as in the reference game): `stackable` pieces (a TV, a lamp) can stand on `surface` pieces (every table; counters and cabinets marked `surface` in furniture.json) as well as on the floor. A stacked piece (`PlacedFurniture.StackedOn`) blocks no cells, is drawn at the surface's height, moves with it, and goes to storage with it. `FindAt` returns the floor piece.
   - **Wall pieces** (`FurnitureKind.WallDecor`, `RestaurantLayout.Walls.cs`): windows, pictures and the menu holder hang on a back wall over `sizeX` wall cells (`PlacedWallItem`: side + index from the back corner), never on the door's cell or each other, and take no floor. They are owned, bought and stored like other furniture and saved in `LayoutSnapshot.wall`. Every restaurant starts with the free menu holder (its `tapAction` "menu" opens the menu when tapped, `WallTapHandler`) and two windows; older saves get the same set.
   - **Decorating** (`RestaurantEditorController`, as in the reference game): tap a piece to pick it up, it follows the finger or mouse, and a tap drops it (touch: drag and lift drops it; a tap without a drag keeps it in hand with rotate / store buttons beside it). Pieces come from the shop bar along the bottom (Shop / Storage tabs, category filters); dropping a held piece on the bar puts it in storage, and "store all" empties the room. On touch a card can be dragged straight up out of the bar, and a new piece is aimed a little above the fingertip so it stays visible. What is in hand floats, its footprint pulses and a marker bounces over it (gold = fits, red = blocked); dragging it to the edge of the view, or past it, scrolls the room. Floors: with a floor chosen, a drag paves the whole rectangle it covers in one undo step (`LayoutEditor.PaintArea`); a tap paves one tile. Wallpaper (theme `wallpapers`, plus the prototype catalog's 48 in `Content/<pack>/RefProto/wallpapers.json`) is per wall cell (`RestaurantLayout.WallpaperAt`, saved as `LayoutSnapshot.wallpaperLeft/Right`): press on a wall and drag along it (`LayoutEditor.PaintWall`), or paper all walls (`FillWalls`). While a floor or wallpaper is chosen a chip at the top names it (X puts it down), the mouse hover outlines the cell and a marker bounces over the area. The chosen floor or wallpaper is previewed live on the hovered or dragged cells (put on the draft and taken off again; the view redraws floor and walls once per frame). Mouse: click to pick up and click to drop, or press-drag-release (shop cards too); right click, R, Q or E rotates; Delete or Backspace stores; the status line names these controls. Wall pieces and the door slide along the walls. Nothing is saved until Save.
   - **Outside the walls:** the door sits on the back-left wall (moved in the build editor, waiting area follows). Beyond that wall runs the sidewalk (`StreetWidth`, right along the wall; `StreetGap` can add lawn in between; the road beyond is scenery). Guests walk the sidewalk's middle lane, turn in on the door's row, and leave the same way (`SimSettings.StreetWalk`); only explicitly marked outdoor decoration (outdoorDecor, decor/plants only) can stand in the designated side cells. Indoor decoration is rejected beyond the floor; legacy indoor pieces saved on the street return to storage with their owned counts preserved. More outdoor space is the **terrace** (`RestaurantLayout.Terrace.cs`, the reference game's outside area): bought in order from the for-sale sign on the lawn in front of the street-side corner (`TerraceSignView`, `TerraceSaleDialog`), sizes, levels and prices in rules.json → `terraceSteps`, checked by the server (`ILandPurchaseServer.CommitTerrace`). It extends the floor from the room's front-left edge (`TerraceWidth` x `TerraceDepth`), has no walls, moves forward when the room grows, and is paved with `theme.terraceFloor`. The grid covers room and terrace; other cells are blocked. `RoomWidth`/`RoomHeight` are the room, `Grid` the whole floor. Behind the back-right wall (three rows back, three cells in from the back corner, as in the reference game) is the fenced 6 x 6 farm (`Garden`): nine 2 x 2 plots opened at the sheet's `gardenPlotLevels`, seeds at `seedCost`, growth only while watered (`wateringHours`), on the wall clock. Everything outside the walls is drawn behind them.
   - **Owner:** the player's avatar works in the restaurant as a free extra worker (`owner` staff types, outside the caps, never dismissed). The Staff panel switches their job between chef, waiter and cleaner (`RestaurantSession.AssignOwner`). Staff types can be drawn by `AvatarPainter` from an `avatar` part list in `staff.json` instead of sprites.
8. **Offline-first.** The game must stay fully playable with no connection.
   - **Local save:** `LocalSaveStore` writes `SaveData` to `persistentDataPath`. It writes to a temp file and swaps it in, every 30 s and on pause or quit. Stress mode never saves.
   - **Idle progress:** `OfflineProgress` estimates what staff did while the app was closed or backgrounded. It works from throughput (staff, stoves, seats, menu, guest arrival rate), scales by the economy sheet's `offlineRate` and is capped at `offlineCapHours`. A clock set backwards counts as zero time.
   - **Sync later:** every player action (sales, recipes, hires, rest, items, market, garden, renovations, terrace, menu, rename, machine uses and repairs, unhappy guests) is recorded in `RestaurantSession.ServerLog` and saved beside the game save (`online_sync_<pack>.json`). The next sync uploads it through `POST /sync/ledger`; the server re-validates every entry (its own prices and its own clock for idle time, which the client never sends) and returns the authoritative state. Never trust the log without that check. `OfflineLedger` is still kept for local display and older saves.
   - **Entertainment** (`RestaurantSim.Entertainment.cs`, rules.json -> `entertainment`): guests prefer dining seats, otherwise reserve a free working machine reachable from its front. They play for `playSeconds` (30), pay `coinsPerUse` (1) automatically, and leave without an unhappy-demand penalty. Native interactive entries use `FurnitureKind.Entertainment` under Functional. Uses break machines at `BreakCount`; cleaners or a player tap repair them. Wear follows moves, Undo and layout snapshots; legacy functional counts also load from `SaveData.toiletUses`. `LocalEconomyServer.SubmitEntertainment` validates catalog kind, payout and unique receipts. Income is ledgered as `EntertainmentIncome` pending backend validation online. Preserve workbook XP rules: no extra entertainment XP, meal count or ingredient rewards. Native on/off/broken frames follow machine state; guests have hand motion and a localized progress indicator.
   - **HUD menus** (`HudDrawer`): Actions and Explore start collapsed. Their 156 x 148 buttons open in two columns; one drawer opens at a time. Choosing a function collapses its drawer. Separate large handles allow closing. Controls use the safe area and localized labels.
9. **Session and progression** (`Logic/Session/RestaurantSession.cs`) wire the sim to the progression systems in `Logic/Progression`. The Unity layer creates one session, calls `Tick` and draws its state.
   - **Economy sheet:** the designers' workbook `Docs/Design/Global_FnB_City_Economy_*.xlsx` is the source of every progression number. DemoRestaurant > Content > Import Economy Sheet writes `economy.json` (`EconomyTable`, formulas in `EconomyFormulas`); never edit that file by hand. `RestaurantSession.Tuning` exposes it.
   - **Restaurant level** (`RestaurantProgress`, on the profile card): one level replaces the old popularity and player levels. XP comes from serving dishes and learning recipes; XP to next = `xpCurveBase + xpCurvePerLevel × level`. Each level-up pays coins and can raise menu slots and staff slots (Levels tab). It never goes down and stops at `phase1MaxLevel`. Dishes, furniture, guest types (`minLevel`) and staff roles unlock by this level.
   - **Demand** (`RestaurantDemand`, popularity, rules.json → `demand`): every happy guest (paid) adds `perHappyGuest`, every unhappy one (turned away, gave up queuing, no table, angry) removes `perUnhappyGuest`, and it fades by `closedDecayPerHour` while the restaurant is closed (no chef or no waiter on duty, also offline). It stays between `min` and `max` and sets the arrival rate: `demand × guestsPerMinutePerDemand` guests a minute (`CustomerArrivals`). There is no daily guest limit. The old star rating is gone (save v6).
   - **Patience:** customers queue in `RestaurantLayout.WaitingSpots` when every seat is taken (`rules.json` → `waitingSpots`; 0 as in the reference game, so a guest who finds no seat leaves unhappy). They give up after `patienceSeconds` and are turned away if the queue is full. After ordering they leave angry after `foodPatienceSeconds`.
   - **Ingredients and recipes:** ingredients currently come only from `IngredientMarket` (timed baskets); further sources are still being designed (customers do not give ingredients). Recipes are learned and upgraded from the list (`RecipeBook.Train`, `RestaurantSession.TrainRecipe`): each level uses one ingredient set (`ingredientSetsPerUpgrade`) and learning adds the dish to the menu. There is no ingredient experimenting. Dishes have a `category` and an `unlockLevel`; above the level, training returns `LevelTooLow` and uses nothing.
   - **Staff:** one staff type per role (chef, waiter, cleaner) with its walk and cook speed in `staff.json`. All roles share the level's staff slots; the next hire costs `hireBase + hirePerMember × team size`.
     - Energy (0–100) drains while on duty, including waiting for work and offline idle time. Speed is multiplied by the energy band: 80+ ×1, 60+ ×0.8, 40+ ×0.5, 20+ ×0.3, below ×0.05 (`rules.json` → `staffEnergy`).
     - Resting goes off duty; staff finish their current job first and return to work automatically when full. Items (`items.json`, bought with coins) restore energy instantly. "Refill all" in the Staff panel (`RestaurantSession.RefillAll`) uses items on the most tired staff first until everyone is full or the items run out.
   - **Profile** (`Logic/Profile`, opened from the top-left card): `PlayerProfile` holds a stable player id (guest until linked), the display name and the avatar.
     - Names follow `NameRules` (3–16 visible characters, any script, small local blocklist; the server filter is the real gate) and `nameChangeCooldownHours` (the first rename is free). Renames and avatar changes are ledgered.
     - Avatar parts come from `avatar.json` (slot, colour, `unlockLevel` by restaurant level). `AvatarPainter` draws them procedurally until layered art exists.
     - Account linking: Android shows Google Play Games; iOS shows Sign in with Apple next to Game Center (App Store guideline 4.8). The buttons are placeholders until the backend supports them (email sign-in works today).
     - Settings (`GameSettings`, PlayerPrefs, per device): music volume, language, frame rate, help/legal links from `theme.json`, and "Delete account & data" (required by both stores once accounts exist).
   - **Tuning** outside the economy sheet lives in `rules.json` (market, cleaning, staff energy, starting ingredients and items). Recipes, categories and stars are in `dishes.json`; rarity and garden grow time in `ingredients.json`; patience and expectations in `customers.json`.
   - Market grants, tips and recipe unlocks are client-side for now. Like coins, they must move to server validation before launch.
10. **Online features are asynchronous.** Friend visits load a server snapshot, and gifts go to a server-side mailbox. There is no real-time multiplayer.
11. **Performance**
   - Static room parts (floor, walls, fixed decor) are merged into large layers.
   - Only characters and movable furniture are separate sprites.
   - Characters are layered (body, head, outfit) under one `SortingGroup`.
   - Mirrored sprites cover two of the four facings (`FacingUtil.IsMirrored`).
12. **Plan for account linking early:** Google Play Games, Game Center / Sign in with Apple, and later Steam.

## Isometric conventions

- Grid +X runs down-right on screen and +Y runs down-left. Cell (0,0) is the back (top) corner. The back-right wall lies along Y = 0 and the back-left wall along X = 0.
- `IsoProjection.GridToWorld`: one cell is 1 × 0.5 world units, one unit of object height is 0.6 world units, and art is 128 PPU.
- **Rotation:** furniture defs and art face SouthWest (front toward +Y, long side along X). Facing SouthEast or NorthWest turns the footprint 90° (`PlacedFurniture.IsRotated`), and the renderer mirrors the sprite.
- **Art pipeline:** sprites live in `Assets/_Game/Resources/Art/<set>/` and are imported by `ArtImportRules` with a bottom-centre pivot, then packed into a Sprite Atlas (DemoRestaurant > Build Concept Sprite Atlas).
  - `RestaurantView` fits each sprite to its footprint width × `artScale` from furniture.json, so the art doesn't need an exact pixel size.
  - Wall art is drawn for the back-right wall and mirrored for the back-left wall.
  - Any missing sprite falls back to the procedural `PlaceholderArt`.
- **Skins (reskinning):** `theme.json` `skins` lists Resources folders tried before `artFolder`, most preferred first (`ArtLibrary.For`). A skin is a folder of sprites named by the art keys content already uses (`table01`, `wall01`, `floor_wood`, ...) plus an optional `skin.json` (`SkinManifest`). `tilePixelWidth` draws sprites at native size; `wallCellsPerSegment` is how many cells one wall sprite covers; per-key hints are `mirror`, `scale`, `groundCorners` and `surfaceCorners`; `backgroundColor`, `roadColor` and `sidewalkColor` set the scene colours; furniture hints `frontCells` (art drawn over cells in front, e.g. a stove mat) and `seatHeight` (chairs). Native-size art narrower than its footprint is centred on it. `street_tile` (with an `anchor`) is repeated along the street; with a skin wall one cell wide, the door cell is left open as a doorway. Optional art: `<door>_open_00..` animates the door while a guest is at it, and `garden_field`, `garden_plot_locked`/`_empty`/`_wet_00..03` draw the farm. Hints in furniture.json and theme.json describe the base art only, so a skin never inherits them. To reskin, add a folder and list it first.
- **Prototype reference assets:** `Tools/RefProto/import.ps1` builds the `Art/RefProto` skin from the private asset export in `Builds/Exports`, using the mapping in `art_map.json`. Prototype music sits in `Audio/RefProto`. `Tools/RefProto/catalog_import.js` turns the export's item catalog into prototype furniture, floors and English names (`Content/<pack>/RefProto/`, `Localization/RefProto/`, `art_map_catalog.json`, all git-ignored), which `ContentLoader` and `Loc` merge in when present. Every `Resources/**/RefProto` folder is git-ignored. `RefProtoBuildGuard` blocks ordinary player builds while one exists; private device testing is allowed only inside the Android build menu's temporary scope, with `BuildOptions.Development` and an output ending in `-private-prototype.apk`. The test APK menu automatically uses this mode when reference resources exist. Never commit these assets or include them in release builds.
- **Street front:** `Tools/RefProto/exterior_import.ps1` turns the export's shop-front catalog into prototype exterior pieces under neutral names (`ext_<kind>_NN`, generic display names such as "Window 3"): sprites in `Art/ExteriorAssets/RefProto`, items in `Content/<pack>/RefProto/exterior.json` (merged by `ContentLoader`), names in `Localization/RefProto/exterior_<lang>.json`. Wall textures repeat over the front. Roofs come from the clean vector export, with `mc_rect` authoring markers removed before rasterization: those markers can cover real roof artwork, so removing black pixels afterward loses the lower roof. Marker widths still determine attachment scale. Native roof registration (`roofAnchorX/Y`, extracted by `ExportRoofMetrics.java`) meets the wall top, including sprites whose branches extend below it; one fixed frame across playable levels reserves space for the largest reachable facade and the catalog's roofs, so changing roofs never moves or scales the facade or its fixtures; markers/flip/store controls share the roof's scaled bounds. Legacy `wallTop` crop metadata is ignored. Signs have the placeholder text painted out. All generated reference assets remain git-ignored.
- **Shop front size** (`ExteriorCatalog.BoxFor`, exterior.json → `buildingSteps`): as the reference game's building bases, the street front grows with the restaurant level (the source's building bases at that scale, from 800 x 318 design units, growing up from the pavement; a fixed street scale keeps upgrades visibly larger), and never shrinks, so pieces placed earlier stay valid. Placement is checked against the level's front; roofs scale with its width and rest on its top edge. The open street listens to session level-ups and redraws the enlarged wall immediately, preserving the draft, owned items and fixture positions. Keep the existing 5/10/15/20/30/40 visual tiers; the workbook's playable cap and economy values are unchanged.
- **Baked characters:** `Tools/RefProto/AvatarBaker/bake.sh` renders the reference 3D avatar (the export's `model.xml`, a rigged COLLADA model whose clothes and face are layers composited onto one texture) in a throwaway batch-mode project, so the Editor can stay open. It writes frames to `Builds/Exports/Characters` and `art_map_characters.json` (git-ignored) for `import.ps1`. Looks per character are in `BakeAll.cs`. Content names a frame set with `animKey` (customers.json, staff.json); `CharacterFrames` loads `{animKey}_{walk|carry|hold|idle|cook|sit|eat|clean|fix}_{f|b}_NN` (f faces SouthEast, b NorthEast, west facings mirrored; `anchor` is the floor point, `hand` where a carried plate sits). `{animKey}_portrait` (baked too) is the head-and-shoulders picture on the profile card and in the staff list. When a skin has them they replace the walk rig, seated sprites and the avatar painter (the owner too); without them the old drawing is used.
- **Concept art:** `Tools/SpriteSlicer/slice.ps1` cuts the concept sheet into those sprites, using the crop boxes in `concept_sheet_boxes.txt`. These are stand-ins until the designers deliver real art.
- **Native meal export:** run `Tools/RefProto/serving_export.py` before `import.ps1`. It works on copies of the archived SWF and freezes the nested `mc_plate` timeline at recipe grades 1–10, as the source `DishOrder` does. General sprite exports otherwise cycle the plate/coaster grade while the food is being eaten. Its `art_map_servings.json` and images are generated/private. `<servingSprite>_level01_00..` through `_level10_00..` are selected by `RestaurantView.RecipeLevel`, wired to the session's recipe book. Replacements may omit these variants and provide a plain serving sprite instead.
- **Serving presentation:** dishes may supply `servingSprite` separately from their UI `icon`. A single sprite or `<key>_00..` sequence is supported. Native-size skins preserve the source pixels per floor cell, with a shared animation crop and `anchor` at the plate/saucer base; fallback art uses `DishPresentation` sizing. Full meals appear on stoves and in hands, eating advances through the original frames, and the final frame remains as the empty plate/bowl/cup until cleaning. The sim retains each dirty seat's meal for this purpose (`DirtyDishFor`). The Malaysian waiter uses the empty-hand avatar renderer; only a collected order adds the carried meal. Back-view stove art missing its baked front mat gets a floor-plane `FurnitureWorkMat`, which follows preview visibility. The Malaysia theme's music multiplier is 1, so the player's music slider can use the full AudioSource range.
- **Draw order:** `IsoDepthSorter` (logic, tested) runs a topological sort on footprints every frame and writes `sortingOrder`. Do not rely on Y-sorting or the transparency sort axis, because they break for multi-cell objects.
- **Wall decorations** (windows, posts, frames) are drawn on the wall plane, so they follow the isometric slope. They are never axis-aligned rectangles.

## Layout

```
Assets/_Game/
  Scripts/Logic/      DemoRestaurant.Logic: pure C#, no UnityEngine
  Scripts/Game/       DemoRestaurant.Game: rendering, input, content loading, scenes
  Scripts/Editor/     DemoRestaurant.Editor: menu tools (DemoRestaurant/...)
  Tests/EditMode/     DemoRestaurant.Logic.Tests
  Resources/Content/<country>/   dishes.json, ingredients.json, furniture.json, customers.json, staff.json, rules.json, theme.json
  Resources/Localization/        en.json, ms.json, zh.json
  Scenes/
```

Content moves from Resources to Addressables once packs become downloadable. `ContentLoader` is the only code that knows where the files live.

## Workflows

- **Run tests:** in Unity, open Window > General > Test Runner > EditMode > Run All. From the command line, close the Editor first and run:
  `"C:\Program Files\Unity\Hub\Editor\6000.6.4f1\Editor\Unity.exe" -batchmode -projectPath . -runTests -testPlatform EditMode -testResults Logs/test-results.xml`
- **Demo scene:** use DemoRestaurant > Create Stress Test Scene, then press Play. It starts in Game mode (guests arrive by rating and level). The debug overlay's Mode button switches to Stress mode (fixed customer count, no staff slot limit) for FPS tests.
- **Android settings:** use DemoRestaurant > Apply Mobile Player Settings (IL2CPP, ARM64, landscape).
- **App icon and splash:** put `app_icon.png` (1024 square), optional `splash_background.png` (landscape key art) and `splash_logo.png` in `Assets/_Game/Branding`, then run DemoRestaurant > Apply App Icon and Splash. The Unity logo is off (allowed on every Unity 6 plan).
